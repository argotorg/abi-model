|---|---|

| Area | ABI encoding, `ABITuple` wrapping a dynamic value |

| Status | fixed |

## Fixes

- solcore (Haskell): https://github.com/argotorg/solcore/pull/620
- solcore-rs: https://github.com/argotorg/solcore-rs/pull/90

## Summary

In `std/std.sol`, `ABIEncode<ABITuple<tuple>>` writes the tail pointer of a
*dynamic* tuple to `basePtr` instead of `basePtr + offset`:

```solidity
} case false {
    // store the length of the head in basePtr
    mstore(basePtr, tail - basePtr);   // should be basePtr + offset
```

The pointer overwrites the first word of the enclosing region, and the tuple's
own head slot is never written. The output is only correct when the tuple sits
at head offset 0, which is why the existing tests (top-level `ABITuple`s)
passed.

## Reproduction

[`case13.sol`](case13.sol) is the contract generated by `abidiff` for the model
case `pair word (tup (array word)) = (9, tup [5, 6])`:

```solidity
let v : (uint256, ABITuple<memory<DynArray<uint256>>>) = (9, ABITuple([5, 6]));
return abi_encode(v);
```

[`case13.json`](case13.json) is the matching `testrunner` file (format of
Solcore's `test/examples/dispatch/`), whose expected return data is the
model's prediction. Return data, word by word (`abi_encode` returns `bytes`,
so words 0 and 1 are the `bytes` offset and length):

| word | role           | expected (model) | actual (Solcore) |
|------|----------------|------------------|------------------|
| 0    | bytes offset   | `0x20`           | `0x20`           |
| 1    | bytes length   | `0xc0`           | `0xc0`           |
| 2    | `9`            | `0x9`            | **`0x40`**       |
| 3    | tuple offset   | `0x40`           | **`0x0`**        |
| 4    | array offset   | `0x20`           | `0x20`           |
| 5–7  | length, data   | `2, 5, 6`        | `2, 5, 6`        |

The tuple's offset (`0x40`) lands on word 2, erasing the field `9`, and word 3
(the tuple's head slot) is left as `0`.

The same bug shows up inside a dynamic sum, where the branch is encoded at
offset 32 of the sum body: the pointer then overwrites the **tag**. For
`inl(ABITuple(ABITuple([])))` of type
`sum<ABITuple<ABITuple<memory<DynArray<uint256>>>>, ()>` the tag becomes `0x40`,
and since the decoder treats any non-zero tag as `inr`, the value decodes as the
wrong constructor.

To rerun the case with the testrunner, put both files under Solcore's
`test/examples/dispatch/` (or rerun `nix run .#diff` against `a7b7afb`; the
case is `case13` of `AbiDiff/Cases.lean`).

## Fix

One line in `std/std.sol`:

```diff
-            mstore(basePtr, tail - basePtr);
+            mstore(basePtr + offset, tail - basePtr);
```

Both PRs add the same regression test (expected bytes from the Lean model):
`encodeTupleAfterField()` for `(9, ABITuple([5, 6]))` and `encodeTupleInSum()`
for `inl(ABITuple(ABITuple([])))`.

With the fix, the abi-model differential tests agree on all cases: fixed cases
20 / 20 (was 19 / 20), and `--random --seed 2 --n 150` 150 / 150 (was
149 / 150).

## Note on the decoder

`ABIDecode<ABIDecoder<ABITuple<tuple>, reader>, …>` also reads the pointer at
word 0 instead of at `currentHeadOffset`, but no program can reach it: its
constraint `tuple: ABIDecode<tuple_decoded>` is never satisfied by a real
payload, and the dispatcher decodes arguments with the raw tuple type. It was
left unchanged.
